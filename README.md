## 🌟 核心特性

- **🎮 多卡 GPU 实时拓扑**：实时采集显存占用、利用率、温度与功耗，支持 8 卡 / 16 卡矩阵感知与自动轮询。
- **🩺 环境合规预检**：开箱即查 `ACS`、`IOMMU` 隔离关闭状态及 `CPU Governor (performance)` 运行模式，确保多卡通信最佳性能。
- **🔄 多机即插即用 (Multi-Host Adapter)**：顶栏一秒切换算力机，标准工程范式（`/home/workspace`）自动复用与服务自适应发现。
- **🐳 容器编排与三大透视**：
  - **脚本源码在线 IDE**：集成微软 VS Code 原生 **Monaco Editor**，支持实时 Shell 语法高亮、Tab 缩进与 `Ctrl+S` 安全热保存（Base64 双向防截断传输）。
  - **Compose 编排解析**：精准提取 `docker-compose-models.yml` 对应服务定义与启动指令。
  - **容器实时日志**：最近 250 行 `docker logs` 动态拉取与一键复制。
- **📈 性能常规巡检 (run.py)**：穿透容器执行短/长上下文及 SLO 极限摸高压测，**SSE 流式推流**实时回显终端输出。
- **🌐 MCCL 通信基准**：一键执行 16 进程 1GB AllReduce 带宽测试与节点连通性验证。
- **💬 模型试玩 (Playground)**：直连推理服务端口，实时测算响应速度（Tokens/s）与耗时。
- **🤖 AI Agent 友好 (Headless Ready)**：暴露标准 RESTful JSON API，无缝对接自动化评测与调度 Agent。

## 📜 大模型纳管与服务工程规范（SOP）

为保障多卡高算力环境下的集群稳定性、防止服务相互干扰与配置污染，平台所有大模型接入与运维必须严格遵守以下工程规范。

### 1. 目录组织与集中管理规范

**【决策结论】强烈建议将启动脚本与 Compose 统一收口在专属目录管理。**

算力机（如 `/home/workspace/`）根目录不应直接平铺各散乱脚本，规范架构如下：

```text
/home/workspace/
├── model-services/                 # 🎯 模型服务与编排专用管理目录
│   ├── docker-compose-models.yml    # 全局统一 Compose 编排文件
│   ├── scripts/                     # 🚀 所有在线模型的专属启动脚本
│   │   ├── start_vllm_qwen3_8_27b.sh
│   │   ├── start_vllm_qwen3_235b_a22b.sh
│   │   ├── start_sglang_deepseek_v4_flash.sh
│   │   └── ...
│   └── scripts_archived/            # 📦 下线/删除模型的历史启动脚本归档库
├── ... (其他工程组件/测试套件)
```

> **平滑兼容原则**：对于老容器（容器内挂载 `/home/workspace:/workspace` 并直接执行 `/workspace/start_xxx.sh`），在执行目录规整时需保留根目录软链接或双向映射，严禁直接硬性搬移中断线上正在运行的容器。

---

### 2. 核心铁律（强制执行）

#### 🔴 铁律一：启动脚本千万不能复用（一模型一脚本）
- **一对一强绑定**：每个模型、每种量化精度（BF16/W8A8/FP8）、每套推理引擎（vLLM/SGLang），**必须拥有专属、独立的启动脚本**（如 `start_vllm_minimax_m2.5_w8a8.sh`）。
- **严禁跨模型共用**：不同模型输入输出结构、分块参数、显存预占（`gpu_memory_utilization`）、TP 分配截然不同，严禁复用脚本。
- **配置隔离防污染**：任何启动参数修改只在专属脚本内生效，绝不允许跨模型传参。
- **生命周期随动归档**：在平台删除或下线模型时，其专属脚本自动移入 `scripts_archived/` 目录归档留痕，绝不污染现行生产环境。

#### 🔴 铁律二：命名规范与规格全称
- **严禁模糊简写**：必须使用能精准识别模型规格的规范全称。
- **MoE 模型全称**：必须标注总参数量与激活参数量。例如：
  - ✅ `Qwen3-235B-A22B`（严禁写成 `Qwen3-235B`）
  - ✅ `Qwen3.5-122B-A10B`
  - ✅ `Qwen3.6-35B-A3B`
- **量化与变体明确**：量化模型必须包含版本后缀，如 `MiniMax-M2.5-W8A8`、`DeepSeek-V4-Flash-0731-W8A8`。
- **驱动版本无需手动拼接**：MACA 驱动版本（如 `MACA 3.8.2.105`）由工作台自适应解析镜像并展示在引擎徽章旁，模型卡片名称严禁人为拼接 `(MACA 3.7.1.2)` 等多余后缀。

#### 🔴 铁律三：Compose 集中编排与精准隔离
- **统一纳管**：所有算力服务必须统一在 `docker-compose-models.yml` 集中定义，严禁散落在宿主机起临时裸容器。
- **Service 命名一致性**：服务命名遵循 `<engine>-<model-name>[-<quant>]`，如 `vllm-qwen3-5-235b`。
- **删除原子性**：删除模型时，平台会精准安全地切除 Compose 中的对应 `service` 块（保留 `.bak` 备份）并停止容器，**绝不触碰或删除任何模型权重文件与底层 Docker 镜像**。

#### 🔴 铁律四：端口与 GPU 卡号资源防冲突
- **端口台账**：严格按服务分配唯一端口（如 8000、8001、8002...），启动前必须通过 `lsof -i :<PORT>` 或平台看板预检。
- **GPU 物理卡号隔离**：多卡服务严格规划 `MACA_VISIBLE_DEVICES` / `CUDA_VISIBLE_DEVICES`（如 0-7 卡跑 A 模型，8-15 卡跑 B 模型），严禁卡号交叉导致多进程 OOM 爆显存。

### 3. 新增模型标准化接入流程（SOP）

当算力机需要上线一款新模型时，必须严格执行以下 4 步走标准流程：

```text
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ 步骤 1: 准备权重 │ ──▶ │ 步骤 2: 编写脚本 │ ──▶ │ 步骤 3: 编排接入 │ ──▶ │ 步骤 4: 启动验证 │
└─────────────────┘     └─────────────────┘     └─────────────────┘     └─────────────────┘
```

1. **步骤 1：模型权重下载与落盘**
   - 新模型统一从 ModelScope 下载至主力存储服务器 `192.2.56.76:/data/AI_model/`；
   - 分发至计算节点对应路径（如 `/home/workspace/models/<模型全名>/`），目录命名与官方 Repo 严格一致。

2. **步骤 2：创建独立专属启动脚本**
   - 在 `scripts/` 下创建独立的 `start_<engine>_<model_name>.sh`；
   - 显式声明环境变量、TP 卡数、最大并发、显存利用率及 `--served-model-name`；
   - 赋予执行权限：`chmod +x scripts/start_<engine>_<model_name>.sh`。

3. **步骤 3：在 `docker-compose-models.yml` 登记 Service**
   - 规划唯一服务名、未占用的主机端口及精准的 GPU 卡号分配；
   - 挂载专属启动脚本与模型权重目录。

4. **步骤 4：平台巡检与基准摸高**
   - 在工作台「模型服务」卡片中点击启动，实时查看 250 行日志直至健康就绪；
   - 使用「性能巡检 (run.py)」执行短/长文本基准摸高，确认吞吐与 TTFT 合格后方可对外开放调用。
